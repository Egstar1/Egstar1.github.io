重新理解安全架构—从建设对象、成熟度到分层落地体系

发表于2026-10-23|更新于2026-11-18|安全建设安全架构
|总字数:13.3k|阅读时长:39分钟|浏览量:

前言

聊安全的人很容易一步跳到工具：WAF、EDR、漏扫、渗透，再往上就是 SOC 和态势感知。可真问到“你们的安全架构是什么”，答案往往就散了——有人说是那张网络拓扑图，有人说是等保文档，有人说就是那套 SOC 平台。

概念一散，落地就走形。我见过不到两百人的公司买了态势感知，装完没人看告警，一年后续费就停了；也见过等保材料堆满一柜子的单位，高危漏洞从发现到修复平均九十天，因为中间没有一条能跑通的流程；还见过三千人公司的安全负责人，架构图画到零信任和数据治理，可他手下只有两个人，图上大半模块没有 owner。

这几次都不是选型错了，是跳过了两个问题：给谁做，现在什么水平。

所以这篇的顺序是：先看清对象，再评估水平，然后回答“安全架构到底指什么”，最后落到分层和运营。前面三章是判断，后面几章是做法。如果你只关心怎么落地，可以直接看第四、五章，但最好还是回头补一下前两章，否则很容易把别人的方案当成自己的。

一、先看清对象：规模决定能做多少，行业决定先做什么

安全架构没有通用模板。约束就两条：组织规模决定你有多少人、多少钱、多少时间；行业属性决定你必须先满足什么。

1.1 小微企业：安全是 IT 的副业

五十到三百人，IT 一到三个人，没有人专职做安全。预算通常没有独立科目，钱从 IT 采购或项目成本里出，一年几万到几十万，多数是一次性支出。

推着他们做安全的不是规划，是四件事：合同里的安全条款、被监管通报或被薅了一次、平台入驻审核、老板刷到同行的泄露新闻。

一年下来大概是这样：三月客户要等保报告，找机构突击补材料；六月新系统上线前请人做一次渗透，改掉几个高危；九月收到云厂商的漏洞提醒，运维连夜打补丁；十一月大促前临时开高防；中间不定时有人点了钓鱼邮件，重装系统了事。

能买的东西其实不多：云上的开箱能力（云防火墙、WAF、主机安全、日志审计、堡垒机按量开通）、等保测评、单次渗透、按次应急。不能买的是 SOC、态势感知、自建 7×24，不是买不起，是买了没人养。这类系统的价值八成来自持续运营，没有人，它就只是一块屏。

所以小公司的架构目标就三句话：底线合规能过，常见攻击能挡，出了事有人兜。形态是“云上开箱能力 + 外部专家服务 + 一份自己的资产台账”。

有条原则值得单独说：能力可以外包，台账和责任不能外包。服务商能替你测、替你值守，但答不了“我有哪些资产、哪个最值钱、谁负责”。这三个问题答不上来，换几家服务商都得从头讲一遍。

最常见的失败不是买错，是买了不做配套动作。日志审计装了不看，堡垒机装了运维绕过去直连，渗透报告锁在抽屉里，复测率是零。

1.2 中型企业：一两个人扛一条线

三百到三千人，有明确的安全负责人，下面零到两个人。团队挂在 IT、研发或技术中台下面，不是一级部门，预算和话语权都受限。年预算几十万到几百万。

这个岗位的真实状态不是做体系，是同时打几份工。周一填甲方八十项安全问卷，周二给新版本做渗透顺便看组件 CVE，周三催三十七个漏洞的整改进度，周四跑等保整改的采购，周五处理 DDoS，晚上写复盘。

矛盾就一句话：人少、活多、流程靠人推。具体断在四个地方：

  • 资产：CMDB 一份、扫描器一份、云控制台一份，三份对不上；
  • 流程：漏洞在群里喊，没有工单、没有 SLA、没有复测；
  • 数据：扫描器、WAF、EDR 各一个后台，出事要登四个系统拼时间线；
  • 人：流程长在负责人脑子里，他一休假全停。

最后一条最要命，也最容易被忽略。我给一个判断标准：如果你的安全能力在负责人休假两周后就会停摆，那它不是架构，是个人能力。

建设顺序也就清楚了：先把资产自动发现和统一台账做出来，再把漏洞工单化和 SLA 补上，然后在 CI/CD 里插一道上线卡点，接着把告警收敛到一个入口，最后补应急预案和一次真演练。自建 SOC、自研扫描器、上 SOAR、全量零信任改造，这四件在这个阶段性价比都很低。

1.3 大型企业：能力不缺，缺的是打通

二十到一百人以上，独立安全部或安全中心，岗位开始细分：资产与合规、应用安全、攻防、SOC 运营、数据安全、基础安全、供应链安全。预算千万级，工具链基本齐全。

这一层的痛点不是缺能力，是能力之间不通。应用安全在扫，基础安全也在扫，两套数据两个口径，研发收到两份工单。资产在 CMDB、暴露面在扫描器、告警在 SIEM、漏洞在 Jira，中间没有统一的资产 ID 串起来，查一条告警要人工拼五张表。

再往下是组织问题。系统的结构会镜像组织的沟通结构，资产团队和运营团队不坐到一起，两边的平台就永远对不上账。所以大厂做架构，一半是技术设计，一半是组织和流程设计。

重点也就从“建能力”转成“打通”：统一资产标识，统一漏洞和事件的状态机，统一权限隔离，统一指标口径。

三种规模的差别，可以放在一张表里看：

小微企业 中型企业 大型企业
专职人数 0 1~3 20~100+
年度预算 几万~几十万 几十万~几百万 千万级
主要驱动 客户要求、被动救火 产品防护、客户准入、基础合规 攻击面治理、监管叠加、内控
架构形态 云上开箱 + 外包 轻量平台 + 自动化流程 集成平台 + 常态化运营
关键词 兜底 闭环 打通
最大风险 出事没人管 负责人一走就断层 告警爆炸、风险不闭环

1.4 行业不同，重心会反转

规模决定能做多少，行业决定先做什么。同样三百人，互联网公司和城商行的架构优先级几乎是相反的。

金融。 监管密集：等保三到四级、密评、人行和金融监管总局的科技风险管理要求、证监会对证券期货业的规定、数据分类分级和个人金融信息保护。技术上有几个硬特征：网络分区细，互联网接入、DMZ、生产、办公、开发测试、运维管理各自隔离；生产区默认不能主动出网；运维走堡垒机，重要操作双人复核；变更多在夜间，必须有回滚预案；日志留存六个月以上；重要系统上线前必须过渗透和代码审计。

落地最难的往往不是技术，是误杀兜底。WAF 拦错一笔交易，损失可能比漏洞本身大得多。方案里必须写清楚：能不能旁路观察，能不能灰度拦截，有没有一键放行，回滚窗口多长。在金融做架构，先学变更管理和证据链，再谈新技术。

央国企。 集团、二级、三级多级法人，总部定标准建平台，二级单位落地运维。典型形态是“总部 SOC + 分支探针 + 专线回传”，架构图上要标清楚哪些能力在总部、哪些在分支、数据往哪流。

最大的结构性问题是项目制：立项、招标、实施、验收，验收之后运维预算和编制跟不上，平台“验收即巅峰”。所以做方案时要把运营预算、人员编制、SLA 一起写进项目，否则大概率烂尾。另外资产庞大分散，“三无资产”（无人认领、无人维护、无人知晓）是常态，资产梳理是长期工程，不是一次项目。

政府。 省直、地市、区县是三个世界。省直能自建运营中心、买全套设备、组驻场团队，重保任务多；区县预算紧，一两个人，靠政务云安全池加第三方托管，目标就四条：别被篡改、别中断、别泄密、别被通报。

共同点是政务外网、互联网区、专网隔离，等保加密评，以及“零事故”考核带来的防守惯性——一出事就想下线。好的架构得给出能用的防守手段：限流、灰度、降级、备份快速恢复，不能只剩关机这一招。

互联网。 诉求几乎全来自业务：防爬、防薅、防撞库、防泄露、保可用性。资产高度动态，容器弹性伸缩，人工台账必然失效，自动发现是刚需。攻击面重心在应用层和 API，小程序、开放平台、第三方 SDK、供应链组件都是入口。能力形态偏左移和自动化，SAST、DAST、IAST、SCA 进 CI/CD，漏洞直接进研发的缺陷系统。

制造业。 IT 和 OT 混在一起，工控协议老、设备旧，很多根本打不了补丁。停产的损失按小时算，所以目标排序是：不停产、不泄密、合规。架构重点是办公网、生产网、工控网分层隔离，必要时单向；打不了补丁的设备用补偿性控制——微隔离、应用白名单、只读策略、离线备份。供应商远程运维通道是高频入口，必须收口到堡垒机加审批录屏。

医疗、教育。 预算有限、外包程度高、勒索高发、数据敏感。重点不是建大平台，是账号和远程接入治理、备份恢复、终端防护、网页防篡改。

小微 中型 大型
金融 少见，多服从总行标准 合规达标、上线测试、边界隔离 强隔离、全链路审计、灾备、常态化对抗
央国企 跟总部标准、外包兜底 标准落地、平台接入 统建平台、考核、重保
政府 政务云安全池 + 托管 等保密评、监测处置 自建运营中心、驻场、重保
互联网 云上开箱、外包渗透 自动化、左移、资产动态发现 自研平台、攻防体系、数据安全
制造 边界隔离、备份、终端 工控分区、勒索防护、供应链 IT/OT 统一治理、集团级监测

对象看清了，才谈得上衡量水平。下一章说这个。

二、成熟度：你现在站在哪一级

这里不照搬 CMMI、CMMC，用一套更贴近国内甲方现状的四级模型：初始级、规范级、量化级、自适应级。

先说明三件事，不然很容易用错。第一，成熟度不等于规模，一千人的公司可能停在初始级，两百人的公司也可能摸到量化级，差别在能力有没有被固化成流程和平台。第二，成熟度不等于投入，设备买得再多，没人运营还是初始级；一个表格但每个漏洞都闭环，已经算规范级。第三，允许局部跳级，资产梳理可以一步做到位，运营体系往往必须从规范补起，不用为了整齐刻意压慢某一块。

2.1 L1 初始级：出事才动

安全是事件驱动的，出漏洞、被通报、客户来审、中病毒，才动一下。

判断起来很简单，问几个问题就够了：生产有多少台服务器、多少个域名？三个人的答案不一样，而且都说不全。台账有没有？有，最后一次更新是半年前。漏洞怎么管？群里 @ 一下。工具？WAF 一个后台，主机安全一个后台，日志审计一个后台，互相不通。出事找谁？先问一圈。

这一级的目标是不出重大事故、应付外部检查。该做的也就三件：把资产盘出来，把底线补齐（备份能恢复、边界有防护、账号不共用、终端有杀毒），再找一个半小时内能响应的外部支援。

2.2 L2 规范级：有章可循

从人治走到有章可循，同一件事两个人做，结果差不多。

标志是：台账有人负责，能分核心、重要、一般；制度成文，漏洞、变更、权限、应急都有；有基础检测，定期漏扫，年度渗透；漏洞有责任人、有时限、有复测；合规拆进了日常动作，不是测评前突击；预案至少真演练过一次。

短板也很固定：一切都靠人推，人一忙就停；没有统一平台，数据靠人汇总；没有量化指标，问这个月安全情况怎么样，只能定性描述；业务一变更，台账就滞后；告警看不过来，就关掉一部分。

多数中型企业、预算一般的央国企二级单位、部分地市政务单位都在这一级。

2.3 L3 量化级：靠数据说话

能力被平台固化，管理开始看数。

资产自动发现，多源合并，变更有感知；扫描器、WAF、EDR、日志、代码审计、红队结果汇到一处，用统一资产 ID 关联；风险能打分，漏洞严重性乘资产价值乘暴露程度，输出的是可排序的清单，不再是几百条高危；工单有状态机，SLA 明确；指标月月统计；SDL 和评审嵌进研发流程，安全需求进需求池，而不是上线后补测。

短板是规则偏静态。攻击手法一变种、业务一迭代就要人工调参，策略跟着事件走，而不是跟着业务变化走。还有一种隐性退化：为了报表好看去优化数字，而不是优化风险。

大型互联网企业、省级政务、头部城商行和券商大多在这一级。

2.4 L4 自适应级：架构跟着业务走

攻防形成闭环，安全成为设计约束，而不是最后加的一层。

业务上线或扩容，安全能力自动跟随，策略自动生成、探针自动部署；红蓝常态化，红队的结果直接变成检测规则；高风险事件可以自动隔离、限流、熔断，同时保留人工兜底和回滚；误报率、漏报率有基线，持续调优；安全指标和业务指标打通，能说清每万元投入减少了多少高风险暴露；架构评审是业务架构评审的固定环节。

国内做到这一级的很少，头部大厂、国家级关基单位、头部总行，加上少数安全能力外溢的厂商。

2.5 自评：十个问题，别凭感觉

每条按 0（没有）、1（有但不稳定）、2（稳定可验证）打分，满分 20。

# 问题 2 分的样子
1 十分钟内能说清互联网暴露面吗 平台可查，每日更新
2 资产有唯一 ID 和明确 owner 吗 全公司统一，变更自动同步
3 新系统上线必经安全评审吗 流程强制，未过不能发
4 漏洞有 SLA 和复测吗 工单 + 超期升级 + 复测留痕
5 告警有统一入口吗 一处收敛，按归属分派
6 每条告警有研判结论吗 有结论，误报可回溯
7 预案演练过吗 年度演练，有复盘改进
8 关键操作可追溯吗 堡垒机加审计日志能还原
9 能给出风险排序而不只是漏洞列表吗 结合资产价值评分
10 负责人休假两周，体系还转吗 SOP 加值班可接续

0 到 5 分是 L1，6 到 11 是 L2，12 到 16 是 L3，17 分以上是 L4。分数本身不重要，重要的是看分布。多数公司会呈现“资产 1 分、平台 2 分、运营 0 分”这种畸形结构，短板在哪一层，一眼就看出来了。

三、安全架构到底是什么

前面两章解决“给谁做、什么水平”。这一章回答最容易被讲糊的问题：安全架构指什么，边界在哪。

3.1 先把词拆开

架构至少包含三层意思，缺一层就不成立：

  • 结构：有哪些组成部分，资产、控制点、平台、角色；
  • 关系：它们怎么连，数据往哪流，权限怎么划，谁依赖谁；
  • 演进规则：新增一个系统按什么规则接入，什么不允许出现，变更走什么路径。

很多人画的“安全架构图”只有第一层，一堆框，框之间没有数据流和信任边界，更没有第三层。图看着热闹，落地时无从下手。

给一个能用的定义：

安全架构是一套围绕资产展开的约束、管控、检测、响应与持续优化的分层体系。它回答五个问题：保护什么、为什么保护、用什么保护、谁来运转、怎么越做越好。

拆开就是五块：资产、驱动、能力平台、运营体系、反馈闭环。网络拓扑图只是其中一张，设备清单只是能力层的一部分，等保文档只是合规驱动的产物。

3.2 四个视角，把抽象的东西看具体

只从一个角度看，概念永远是虚的。换四个角度各拍一张，叠起来就实了。

第一个是资产视角：我有什么，哪个最值钱。按业务重要性和数据敏感度排个序，产出是分级清单。后面所有资源都按这个排序分配，核心资产配最强控制，边缘资产用最低成本兜底。

第二个是攻击面视角：谁能打到我，从哪进来。按是否互联网可达重排一遍。直接暴露的，域名、IP、API、VPN、远程桌面；间接暴露的，供应链、第三方、外包运维、员工终端；内部横向的，弱口令、共享账号、过度授权。

这两个视角的差集，往往就是事故来源。你觉得不重要所以没管，攻击者觉得很容易所以打了。

第三个是控制点视角：在哪些位置放了什么控制，是预防、检测、响应还是恢复。一个成熟的布局不是每个位置都堆设备，而是每类风险都有预防加检测加恢复。只有预防没有检测，等于闭眼防守；只有检测没有恢复，等于知道要死但救不回来。

第四个是流程视角：一个风险从发现到关闭，经过哪些人、哪些系统。发现、确认、定级、派单、修复、复测、关闭、复盘。这条链上每换一次系统、每跨一个部门，就是一个断点。架构设计的一大半工作，是消除这些断点。

3.3 拿一条真实链路走一遍

还是抽象，就找个具体业务。假设是电商下单：

用户 App → CDN → WAF / DDoS 清洗 → SLB → API 网关
        → 订单服务（K8s）→ Redis → MySQL
        → 对象存储 / 消息队列 → 第三方支付

沿着这条链，每个位置问四件事：这里有什么资产，跨了几次信任边界，有什么控制，出问题怎么查。

位置 控制点 常见缺口
域名 / DNS 证书到期监控、解析变更审计 证书过期，全站不可用
CDN 回源鉴权、缓存投毒防护 源站 IP 泄露，CDN 形同虚设
WAF 规则防护、Bot 管理、日志留存 只开默认规则，误杀就整条关掉
API 网关 认证鉴权、限流、参数校验、审计 内部接口未鉴权，越权
订单服务 镜像扫描、运行时防护、密钥管理 密钥写死在镜像或配置里
Redis 禁止公网、ACL、持久化 未授权访问，被写公钥
MySQL 最小权限、审计、加密、备份 共用高权限账号，审计缺失
对象存储 Bucket 策略、防盗链、加密 Bucket 公开可读
第三方支付 验签、回调白名单、对账 回调不验签，可伪造支付成功

这一圈走下来，安全架构的意思就具体了：把这条链上每个位置的控制点，按“谁负责、在哪一层、是阻断还是检测、出问题怎么查”固定下来，并且保证新链路按同样的规则接进来。

这个方法比任何定义都好用，因为它可以立刻拿自己公司的核心业务画一遍，缺口会自己冒出来。

3.4 边界：管什么，不管什么

概念不清，多半是边界不清。直接划出来。

必须管的是七件事：安全域与信任边界、控制点布局、身份与权限模型、数据流转与保护、检测与响应、运营流程与职责、度量与演进规则。

不该管的是：具体业务功能怎么实现，服务器怎么装、网络怎么布线，代码具体怎么写（只给规范和卡点），安全产品的内部实现。

判断边界有个土办法，拿具体问题去试。“要不要给这个系统上 WAF”，管；“WAF 用哪家”，参与选型但属于采购；“WAF 规则谁调”，管；“WAF 引擎怎么写的”，不管。

边界清楚，架构文档才不会写成什么都提一句的百科。

3.5 和几个容易混的概念分开

概念 回答什么 产出
安全治理 谁决策、谁负责、政策是什么 组织、制度、责任矩阵、预算
安全架构 结构怎么搭、控制点在哪、怎么演进 分层模型、域划分、控制矩阵、路线图
安全技术体系 用什么组件、怎么部署 产品清单、部署方案、配置基线
安全运营 每天怎么转、告警怎么处理 SOP、值班、工单、指标
安全体系 以上全部加制度考核 完整体系文件和运转机制

治理定规则，架构定结构，技术定组件，运营定运转，体系是全集。这五个词在汇报里经常被混着用，混着用一次，后面就要多开三次会对齐。

3.6 怎么判断一个架构好不好

五条：能一页纸讲清楚；能按规模和成熟度裁剪，L1 用它的两成也成立；每个模块有 owner、有交付物、有验收标准；每个能力对应至少一个指标；写清楚了下一步加什么、什么条件下加。

反过来，一份方案里如果全是没 owner 的名词、没指标的模块、没先后的清单，那多半是抄来的。

四、分层：五层结构，五个切面

前面讲对象和水平，这里讲结构。先看总图。

4.1 L0 基座：我们到底在保护什么

这一层不“做安全”，它是安全的宾语。

资产清单只统计服务器远远不够。实际上要覆盖：网络（出口、专线、VPN、公网 IP、NAT 映射）、云（VPC、安全组、对象存储、负载均衡、API 网关）、计算（物理机、虚机、容器、镜像仓库）、数据（库、缓存、大数据、备份、日志平台）、应用（域名、证书、站点、API、App、小程序）、身份（员工账号、服务账号、AK/SK、第三方账号）、终端、OT 和 IoT、供应链（开源组件、外包厂商、云服务商）。

盲区也集中在几处：临时开的端口映射、离职人员留下的 VPN、安全组开着的 0.0.0.0/0、公开可读的 Bucket、测试域名和历史接口、长期不过期的服务账号。

台账别追求大而全，先把这十二个字段填齐：

资产ID | 名称 | 类型 | 地址 | 归属系统 | 业务负责人
安全负责人 | 业务等级 | 数据等级 | 是否互联网暴露 | 部署位置 | 生命周期状态

再加两个运营字段：数据来源、最后确认时间。资产 ID 必须唯一且稳定，它是后面所有平台关联的锚点。最后确认时间是防腐剂，超过九十天没确认的自动标灰，逼着人去核。

资产工作分三步，不能跳。先发现，云 API、CMDB、扫描器、DNS、证书透明日志、流量，目标是捞影子资产；再登记，去重、合并、补 owner，最枯燥也最有价值；最后分级，按业务重要性、数据敏感度、暴露程度打标签。分级不是为了好看，是为了决定资源投给谁。

资产之上是网络。这一层要回答的不是“网络怎么建”，是“边界在哪、跨边界怎么控”。分区一般是互联网接入、DMZ、生产、办公、开发测试、运维管理、第三方接入七块；南北向出入口收敛，默认拒绝、白名单放行；东西向防横向移动，微隔离、主机防火墙、服务间认证。VPN、远程桌面、数据库直连、第三方运维通道这四个是事故高发口，得单独治。

判断这一层做得好不好，看四个数：资产发现覆盖率、台账准确率、互联网暴露面数量、高危暴露的收敛时长。

最常见的坑是跳过资产直接上设备。你都不知道要保护什么，WAF 和 EDR 不知道该管谁，架构就是空中楼阁。

4.2 L1 驱动：为什么做安全

动力只有两种：怕被罚，和怕出事。

合规这块，来源要看适用性：网络安全法管等保、日志留存（不少于六个月）、事件报告；数据安全法和个保法管分类分级、告知同意、跨境、最小必要；等保管技术和管理两个维度共十个安全类；关基条例管识别、专门保护和年度检测评估；密码法管密评；再加上金融、卫健、教育、证券期货的行业规范。

合规驱动能不能落地，分水岭在于有没有一张“合规条款—控制项—证据—owner”的映射表。比如“身份鉴别”对应双因素和口令策略，落在 IAM 和堡垒机，证据是配置截图和审计日志；“安全审计”对应日志集中和留存，落在日志平台。有了这张表，检查时不用现编，证据平时就在产生。

业务驱动靠的是损失模型。老板不关心 CVE 编号，关心这事会让他损失多少。勒索加密，算每小时营收乘停产小时数加恢复成本；数据泄露，算罚款上限加客户流失乘 LTV；业务中断，算每分钟订单损失加 SLA 赔付；客户准入失败，就是那个大客户的年合同额。

汇报的句式也得换。不要说“我们发现 137 个高危漏洞”，要说“核心交易系统有 3 个可直接利用的高危问题，攻击者不用登录就能拿到订单数据，按监管口径可能触发通报；修复要 5 人日，本周能完成”。

权重不同，建设偏好也不同。合规为主的单位，钱花在制度、审计、隔离、证据链和测评整改上，容易材料齐全但风险没收敛；业务为主的单位，钱花在漏洞闭环、入侵检测、应急和可用性上，容易合规欠账、出事说不清；两边都要的集团，靠平台统一承载，但也容易两套流程两张皮。

从驱动推年度规划，就一条链：业务目标或监管要求，到 Top 10 风险，到控制目标，到项目，到预算和人力，到验收指标。哪个项目在这条链上找不到上游依据，那多半是厂商推的，不是你需要的。

4.3 L2 平台：三类，别混着说

大家最熟的是这一层，也最容易混。拆成三类就清楚了。

功能平台是单点能力，解决一个具体问题。边界防护用防火墙和安全组，Web 攻击用 WAF，网络层检测用 IDS/IPS，可用性用高防，漏洞发现用漏扫和渗透，源码缺陷用 SAST，运行时漏洞用 IAST，开源组件用 SCA，主机威胁用 EDR/HIDS，运维管控用堡垒机，数据访问审计用数据库审计，外发管控用 DLP，钓鱼防护用邮件安全，情报靠威胁情报，最后还有蜜罐和备份容灾。

每种都有局限：防火墙管不了应用层，WAF 被绕过之后没感知，漏扫覆盖不到逻辑漏洞，SAST 误报高，堡垒机会被绕过，数据库审计只审不防，DLP 规则维护成本高，没演练过的备份不算备份。

判断一个该不该买，问三句：它解决我哪个 Top 风险，谁来运维，失效了怎么发现。

技术平台承载流程，是“线”：资产管理、漏洞管理、SDL、IAM、工单、应急响应、知识库。这类平台技术含量不高，价值在于把“靠人记”变成“系统推”。中型企业优先建这一类，比建 SOC 划算得多。

集成平台是数据收口，SIEM、SOC、XDR、态势感知、SOAR 都算。本质是一条流水线：

采集（日志/流量/终端/云审计/情报）
 → 归一化（统一字段、时间、资产ID）
 → 富化（补资产、情报、漏洞上下文）
 → 关联检测（规则、模型、基线）
 → 告警（分级、去重、抑制）
 → 编排处置（剧本、封禁、工单）
 → 度量（MTTD / MTTR / 误报率）

任何一环缺了都会退化。没有资产 ID，告警说不清打的是谁；没有归一化，同一个事件三种写法；没有富化，分析师要手工查五张表；没有处置闭环，告警点完已读就消失了。

三类的关系是：功能平台产生数据，技术平台承载流程，集成平台做关联和调度，不是替代关系。

顺序上，先有资产和漏洞管理，哪怕开源加表格起步；再有三到五个稳定的功能平台，产生可靠数据；然后再考虑集成。触发条件大概是这几个：日均有效告警几百条，人工看不过来；日志源超过十个，工具超过十套；有两个人以上专职研判；已经能说清哪些告警必须处理，只是效率低。

最常见的坑是日志源没接全就上 SIEM，最后只有防火墙日志；买了 SOAR 没有剧本，自动化变成自动发通知；平台不做权限隔离，自己成了最大的越权入口。

4.4 L3 运营：人、流程、职责

平台是工具，运营体系才是骨架。没有这一层，前面的投入都是资产，不是能力。

先说职责。以漏洞管理为例：

环节 安全 研发/业务 运维 资产 owner 管理层
发现 R/A I I I I
定级 R C C C I
派单 R I I A I
修复 C R R A I
复测 R/A C C I I
关闭或风险接受 R C C A C
复盘 R C C I A

R 是执行，A 是最终负责，C 是被咨询，I 是被通知。注意 A 必须落在业务侧，不能落在安全团队。安全负责发现和推动，业务负责修。这条不写清，漏洞永远修不完。

人也得现实一点。一个人就是全包，合规、渗透、运营、应急都归他；三个人可以分成合规与资产、应用安全与渗透、运营与应急；六到十人才谈得上细分。

流程必须有 SOP。漏洞按等级定时限：严重（可直接利用、互联网暴露、核心数据）24 小时临时缓解、72 小时修复；高危 7 天；中危 30 天；低危 90 天或走风险接受。事件按 P1 到 P4 分级：P1 是核心业务中断、数据泄露、勒索加密，15 分钟响应、1 小时上报；P2 是单系统被入侵、大面积钓鱼中招，30 分钟响应、2 小时内控制；P3 是单主机确认告警、异常外联，4 小时内处置；P4 是低风险告警和咨询，工作日处理。

值班有三种现实解法。自建 7×24 至少四五个人才轮得开，金融和大型企业这么干，代价是人力成本和夜班质量；轮值加托管适合中型，前提是升级和授权机制清楚；完全托管适合小微和基层，但自己得有判断力，不能全听服务商的。

指标是这一层的灵魂：MTTD、MTTR、漏洞闭环率、超期率、误报率、覆盖率、演练达成率。别贪多，五到八个够用，关键是每月看趋势。

还有个中型企业最容易忽略的事：让体系脱离个人。三个动作，高频动作写成一页 SOP（谁、什么时候、打开哪个系统、判断标准、升级给谁）；关键流程至少两人会；判断和处置记录在系统里，不要留在微信里。

4.5 L4 优化：让数据回到架构

运营不是做完就结束，得把数据收回来，反向改架构。

输入是这些：告警统计、漏洞闭环数据、红蓝结果、事件复盘、内外部审计、威胁情报，还有业务变化，新业务、上云、出海、并购。

动作有四类。一是度量归因，区分过程指标和结果指标，扫描次数、告警数量是过程，暴露面收敛、MTTR、逃逸率才是结果，后者才能拿来做决策。二是复盘，事件复盘落到流程和架构改动，攻防复盘把红队路径变成规则，项目复盘看投入产出。三是对抗和狩猎，红蓝常态化，紫队协同，红队发现、蓝队建规则、一起验证；狩猎是假设已经被入侵，主动去找痕迹。四是策略迭代，检测规则要有生命周期，上线、观察、治误报、下线；防护策略跟着业务变；架构跟着新场景走。

三个新增面值得单独放进来：数据安全与隐私，分类分级、流转地图、跨境、去标识化，正在从合规项变成架构项；供应链安全，开源组件、外包厂商、云服务商，风险不在你机房但账算在你头上；AI 应用安全，提示注入、数据泄露、模型和 Agent 的权限边界，很多企业的架构里还没有它的位置。

判断有没有真在优化，看一个细节就够了：架构文档有没有版本演进记录。一年下来架构图一次没改，要么业务没变，要么复盘结果没回到架构。后者更常见。

4.6 五个横向切面

资产管理、合规、安全检测、安全运营、风险防控，这五个不是第六层，是贯穿所有层的五个镜头。

切面 本质 输出 形态变化
资产管理 知道保护什么 唯一台账、分级、owner 表格 → 平台 → 自动闭环
合规 满足外部约束 控制矩阵、证据、整改计划 突击补材料 → 常态化 → 自动取证
安全检测 用攻击视角找问题 漏洞、攻击路径、规则 年度渗透 → 定期 → 持续
安全运营 让能力持续转 处置结果、SOP、指标 救火 → 流程 → 平台化
风险防控 做取舍和决策 风险登记册、评分、处置决策 拍脑袋 → 清单 → 量化

为什么是横向？因为它们是看问题的角度。同一台服务器，资产视角看是一条记录，合规视角看是一个测评对象，检测视角看是一个攻击目标，运营视角看是一个告警来源，风险视角看是一个风险载体。五个角度合起来才是完整对象。

做成纵向的五个模块，就会出现典型的组织病：资产团队做的台账合规团队不认，合规要的证据运营不产生，检测发现的漏洞风险团队不知道。横向的意义，是强制这些能力对齐在同一条数据链上。

五、把运营拆成一条流水线

前面讲的都是结构，真正每天在转的是运营。很多单位的问题不在缺能力，而是这条线断在某一段，前后接不上。

运营可以拆成六个环节：资产管理、风险识别、监测预警、分析研判、整改闭环、运营优化。它不是六件事，是一条有进有出的流水线。

5.1 资产管理：流水线的进水口

这一环不是“盘一次资产”，是“让资产进入视野”。

三个动作：登记，新系统上线、新域名解析、新机器开通，要在某个流程里留下记录；归属，每条资产有业务负责人和安全负责人，没有归属的资产等于没人管；分级，按业务重要性和数据敏感度打标签，决定后面资源怎么分。

断点通常在上线流程。安全没有卡点，资产就只能事后补录，补录的东西天然滞后。另一个断点是归属只写到部门，没写到人。部门是一个组织，人才能被 @。

输出是一份能被别的系统直接引用的台账，核心是唯一 ID。

5.2 风险识别：主动去找

四条路：渗透测试验证真实可利用性，上线检测在发布前拦住，代码审计看源码里的逻辑缺陷，风险评估结合资产价值判断严重程度。

产出不该是漏洞列表，而是带优先级的风险清单。同样是高危，一个在互联网可达的核心交易系统，一个在内网测试机，处理顺序完全不同。

这一环容易断在三个地方：只测不判，报告只列问题不给结论；判了不落到人，问题躺在共享盘里；只做一次，不上线不回顾，系统改了三个月没人再看。

5.3 监测预警：把资产真正纳入视野

资产进了台账，不等于进了监控。要确认三件事：日志采到了没有，规则覆盖了没有，告警有人接没有。

流量、主机、WAF、云审计、情报命中，最终要收敛到一个入口，再按资产归属分派。没收敛，就是四个后台轮流登；没分派，就是所有人都能看到，但没人觉得是自己的事。

这一段最常见的假象是“我们有监控”。设备确实都在，日志源只接了一半，告警发到一个没人看的邮箱，或者干脆只在大屏上滚动。

5.4 分析研判：从告警到结论

告警不等于事件。研判要做四件事：确认真不真，判断影响面（哪台资产、什么数据、多少用户），定级 P1 到 P4，决定动作（阻断、隔离、观察、忽略）。

这是最吃人的环节，也是自动化最难替的环节。能自动化的部分其实是富化：把资产信息、漏洞上下文、情报、历史告警自动拼到一条告警上，让人少查五张表。至于“这到底是不是误报”，短期内还得靠人。

研判的产物要能被下个环节直接用：结论、等级、责任方、建议动作。只在群里回一句“看了，没事”，等于没有研判。

5.5 整改闭环：把结论变成动作

漏洞要派单、有时限、有复测、有关闭或者风险接受签字。事件要处置、取证、恢复、复盘。

闭环的标志不是修完了，是有记录、可追溯、能验证。很多团队卡在这里：修了没复测，复测了没记录，关闭了没回写，下一个季度扫描又把同一台机器报一遍。

还有一个常被忽略的点：风险接受也要有 owner 签字和有效期。默认放着不管，不叫接受风险，叫不知道有风险。

5.6 运营优化：让下一轮更准

把前面五个环节的数据收回来，看四件事：哪些资产总是漏，哪类告警误报最多，哪个环节耗时最长，哪条规则从来没命中过。

输出是四类改动：改台账字段，改检测规则，改流程时限，改平台配置。

没有这一环，流水线就是条直线。跑了十二个月，资产还是那批，规则还是那套，误报还是那么多，只是周报多写了十二份。

5.7 闭环断在哪

三个断点，对应三个指标。

第一，资产到监测。台账有了，监控没盖住。指标是资产纳管率，也就是台账里有、监控里也有，占台账的比例。

第二，告警到工单。研判完了，没人派单，或者派了没人接。指标是告警转工单率，以及转单之后的响应时长。

第三，工单到资产。修完了，台账没更新，下次扫描又是一条新记录。指标是修复回写率。

这三个数比“本月扫描了多少次”有用得多，因为它们测的是连接处，而问题几乎都出在连接处。

5.8 指标是一条链

资产覆盖率、检测覆盖率、告警有效率、研判准确率、闭环率、平均修复时长、复发率，这七个是一条链。

前面掉一环，后面全失真。资产没覆盖，检测覆盖率就是假的；检测没覆盖，告警有效率没有意义；研判不准，闭环率再高也只是把误报关得快。

所以看运营看板，别从中间看，从第一条开始看。

六、落地：从水平推到路线

方法四步：识别对象，评估成熟度，按阶段裁剪能力，排出先后。顺序不能反，先补底层再补流程，最后才上平台。

6.1 三套方案

小微企业，目标从 L1 到 L2，一年几万到几十万。

优先级 做什么 验收
P0 资产台账，云控制台加 DNS、证书、漏扫，季度更新 十分钟能说清暴露面
P0 备份可恢复，每季度真恢复一次 四小时内能恢复
P0 边界与账号，云防火墙、WAF 默认规则、禁共用账号、开 MFA 无高危端口裸奔
P1 等保测评和整改闭环 测评通过，问题关掉
P1 年度渗透、主机安全、应急服务商联系方式 高危清零

不做的：SOC、态势感知、自建值班、零信任全量改造。

中型企业，目标从 L2 到 L3，一年几十万到几百万。

优先级 做什么 验收
P0 资产自动发现，多源合并，唯一 ID 覆盖率过 95%，月度更新
P0 漏洞工单化，SLA 加超期升级 闭环率过 90%，超期低于 10%
P0 CI/CD 上线卡点，SAST、SCA、镜像扫描 高危不放行
P1 告警收敛到一个入口，分级分派 不再多平台登录
P1 预案、联系人、年度演练、外部支援 一次真演练达标
P2 季度渗透加关键系统代码审计 高危清零
P2 五到八个指标的月度看板 能向管理层汇报

不做的：自研扫描器、SOAR、全量零信任、自建 SOC。

大型、金融、省直政务，目标从 L3 到 L4。

优先级 做什么 关键点
P0 统一资产底座 唯一 ID 贯穿所有平台
P0 集成平台 数据源接全、归一化、富化、告警治理
P0 运营中心与值班 分级研判、SLA、升级机制
P1 SDL 左移 需求到上线全流程卡点
P1 数据安全体系 分类分级、流转地图、加密脱敏、审计
P1 红蓝常态化 一年至少两轮，结果转规则
P2 自动化响应 先做三到五个高频剧本

6.2 中型企业的十二个月

头两个月盘资产、收暴露面，出台账 v1 和紧急风险清单。三到四月做漏洞流程和上线卡点，把 SOP、工单、CI/CD 门禁搭起来。五到六月做边界和账号治理，分区策略、堡垒机全覆盖、MFA。七到八月做告警收敛。九到十月做应急体系，预案、联系人、一次演练。最后两个月做合规复盘和明年规划。

这个节奏不是标准答案，但顺序有讲究：资产永远第一，因为它决定后面所有数据准不准；应急放在中后段，因为预案没有资产和告警做支撑就是空文。

6.3 六种错配

L1 上 SOC，日志源不全、无人研判，最后只剩一块屏。

只买设备不管账号，EDR 装一半、堡垒机被绕、服务账号长期有效，控制点形同虚设。

合规完成就当安全完成，测评通过但高危常驻，一打就穿。

人少却照搬大厂架构，图上二十个模块，实际 owner 只有两个。

平台先行、资产欠账，平台跑半年，台账还是 Excel，告警全对不上对象。

流程上墙、执行靠人，制度八十页，实际全在群里推进，没有系统留痕。

六种错配的共同点是一样的：都在回答“用什么”，没回答“给谁用、谁来转”。

七、把架构画出来

架构不能被表达，就没法评审，也没法交接。

四张图够用。分层能力图，回答我们有哪些能力、分几层，每个框标 owner 和建设状态。资产与控制点矩阵，行是核心系统，列是预防、检测、响应、恢复。数据流与信任边界图，画数据不画设备，跨边界处标控制点和协议。运营流程图，用泳道画清安全、研发、运维、业务、管理层各自在哪一步，SLA 和升级点标在箭头上。

三条原则。总图一页纸讲完，细节放分图；控制类型、边界类型、数据等级的图例全公司统一；每个框必须有 owner，没有就标规划中，不要假装它存在。

如果要从零写一份架构文档，八节就够：对象与约束、成熟度评估、资产与暴露面、信任边界与域划分、控制点矩阵、平台清单与 owner、流程与指标、演进路线。

八、几个常见误区

有了 SOC 就有了安全运营。 平台只是收口，运营是人按流程在平台上跑。没有研判结论和处置闭环，SOC 只是把多个后台的告警搬到一起。

合规做完就等于架构落地。 测评是抽样、是时点、是基线。等保通过的系统照样可能有可以直接利用的高危。

工具越多越安全。 没人看的工具就是盲区。每加一个，先回答谁运维、数据进哪、告警谁接。

安全是安全部门的事。 安全负责发现、推动、度量，修复和取舍是业务的事。RACI 里最终负责给错人，流程一定推不动。

零信任是一套产品。 它是一组原则：不默认信任、持续验证、最小权限。不改身份和权限模型，买再多也只是贵一点的边界防护。

上了自动化就能减人。 自动化省的是重复劳动，增加的是规则和剧本的维护。流程不稳，自动化只会更快地制造错误。

架构设计一次到位。 架构跟着成熟度、资产和业务在变。一年没更新的架构图，基本等于没有架构。

九、结语

安全架构这个概念之所以模糊，是因为我们总跳过保护对象和所处阶段，直接讨论上层组件。

把顺序倒回来就清楚了：先看给谁做，什么规模、什么行业、什么监管、什么预算；再看在什么水平，L1 到 L4，短板压在哪一层；然后理解架构是什么，资产为根、驱动定向、平台承载、运营落地、优化闭环；最后才谈选什么、先做什么。

它的目标不是零漏洞，是让组织对攻击面、风险和管控手段有持续的感知，并且有一套能迭代的收敛能力。

如果只记一句，记这个：架构不是画出来的，是长出来的。但能不能长对方向，取决于一开始有没有看清自己是谁。
